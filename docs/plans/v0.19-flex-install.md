# v0.19 — symfony/flex with install (first slice)

## 1. Scope

### Problem
`vivacity update` on a Symfony project resolves natively (v0.16 B) but
only with `--no-install`: with install, the command is handed to
Composer, because Flex's `POST_UPDATE_CMD` writes into the project.
That is the last big functional gap for the ecosystem vivacity is most
used in — every `composer update` on a Symfony app.

### What Flex does at POST_UPDATE_CMD (read at v2.11.0, src/Flex.php)
`update()` → `install()`:
1. `.env` copied from `.env.dist` under conditions (already guarded).
2. `fetchRecipes(operations)`: for each operation's package, a recipe
   from the index, **or** — when the package has none — an
   *auto-generated* recipe when `SymfonyBundle::getClassNames()` finds a
   bundle class, whose manifest is `{bundles: {Class: [envs]}}`.
   Packages whose recipe is already locked at the same `ref` are skipped.
3. With no recipe at all: `finish($rootDir)` → `synchronizePackageJson`
   (guarded) + `$this->lock->write()` (symfony.lock) and a
   `Run composer recipes…` line.
4. With recipes: `Symfony operations: N recipe(s)` then each recipe's
   configurators (bundles, copy-from-recipe, env, gitignore, makefile,
   dotenv, container, docker…), then `finish`.
5. `update()` then merges `flex-require`, and `unpack()`s symfony-packs
   (both already guarded).

### Decision — slice it
The whole of 4 is a port of fourteen configurators writing project
files: out of reach in one go, and each one is a parity surface of its
own. The first slice is the case where Flex writes **nothing but
symfony.lock**:

- every operation's package has no recipe in the index, and
- no such package ships a bundle class (no auto-generated recipe), and
- the existing write guards (`.env.dist`, package.json / importmap.php,
  symfony-pack, `flex-require`) already say no.

Then the only file Flex touches is `symfony.lock` — and when no recipe
is added or removed, `Lock::write()` rewrites it only if its content
changed (`JsonFile::write` + `filePutContentsIfModified`). So: native,
with the same stderr lines.

### Non-goals (later slices, each its own plan)
The configurators; recipes that *are* in the index; the auto-generated
bundle recipe; `symfony.lock` entries added or removed; `--reset`.

### Success criteria
1. `harness/update.sh`'s Flex pass gains an install run on the symfony
   and sylius fixtures: project identical to Composer's (symfony.lock
   included), same stderr.
2. A case where a recipe *does* apply still goes to Composer, with the
   reason, before any write (`harness/transitions.sh`).
3. `--no-install` unchanged.

## 2. Plan
1. `vivacity::flex`: `recipes_for(names, index)` — the index already
   fetched for the pool filter carries `recipes` / `recipes-aliases`;
   read which of the transaction's packages have one.
2. `SymfonyBundle::getClassNames` (the auto-generated recipe's trigger):
   ported or refused. Refusing is the conservative first step — but it
   would refuse most installs, so it must be ported: it reads the
   package's `autoload.psr-4` prefixes and looks for a `*Bundle.php`
   class. Measure on the corpus how often it fires.
3. The guard: in `resolution_fallback`, when the command installs and
   Flex is active, compute the operations' packages… which are not known
   before resolving. So the check moves *after* the solve and *before*
   the install: a new hand-over point, `--no-fallback` friendly.
4. `symfony.lock` unchanged: assert it, do not write it.

## 3. Meta-analysis (to be done by a fresh reviewer before executing)

## 3. Meta-analysis — done 2026-09-23 by a fresh reviewer, verdict: abandon this slice

Fourteen findings, the sharpest of which I reproduced by hand before
acting on any of them. The slice as scoped was wrong on three counts:
its condition is computed over the update transaction's operations, but
Flex's come from `recordOperations` at `PRE_OPERATIONS_EXEC` — on the
symfony fixture, 123 install operations are handed to Flex on an update
that prints `Nothing to install, update or remove`; its hand-over point
(`resolve_and_lock`, after the solve) is **after** composer.lock has been
written, which breaks the contract and would make Composer re-resolve
against vivacity's lock on a partial update; and its happy path already
diverges on stderr (the `symfony/thanks` reminder, which
`POST_PACKAGE_UPDATE` arms on any version bump). Both named fixtures also
fail the condition outright (`importmap.php`, `package.json`), and the
harness stages no `symfony.lock` at all. `SymfonyBundle::getClassNames`
reads vendor/, so it cannot be answered before the install for the very
packages a transaction touches — and an error in the permissive direction
silently loses a bundle registration.

Taken instead, in the reviewer's order: **slice A**, closing the Flex
divergences on the paths vivacity already takes natively. Slices B (an
install whose local transaction is empty) and C (reading the candidate
`*Bundle.php` out of the dist in the store) keep their plans for later.

## 4. Execution log
- 2026-09-23, **slice A**: `Flex::install` at `POST_INSTALL_CMD` emulated
  — the `.env` copy under its four conditions (`root-dir` with
  `initOptions`' real precedence: a top-level `extra.root-dir` overrides
  `extra.symfony.root-dir`; `runtime.dotenv_path`) and its two lines,
  gated on `Downloader::isEnabled` (symfony/flex a root requirement).
  `symfony/flex` moves from the benign list to the emulated one. A
  `symfony-pack` no longer gets `: Extracting archive`
  (`SymfonyPackInstaller extends MetapackageInstaller`). The
  `Symfony recipes are disabled: …` line, which `fetchRecipes` writes
  before `install`'s blank line, added to the update path. And, found by
  the new harness: `--no-plugins` prints
  `The "<name>" plugin was not loaded as plugins are disabled.` after each
  plugin's own install line (`PluginManager::registerPackage`), which
  vivacity never printed. Fixture `flex-install` + `harness/flex-install.sh`
  (7 cases, full stderr compared).
