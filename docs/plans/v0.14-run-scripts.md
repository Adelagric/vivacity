# v0.14 — `--run-scripts`: the scripts, run by Composer, in Composer's order

Started 2026-09-17. Level 1 (multi-file, reversible, opt-in flag): plan +
self-checklist meta, review by harness. Decision (with the user): vivacity
never embeds PHP; the scripts are Composer's business, vivacity only
drives them — opt-in, off by default (the contract "vivacity never runs
scripts" stays the default).

## 1. Scope

### Problem

62 of the 105 corpus projects declare install-time scripts
(`pre/post-install-cmd`, `pre/post-autoload-dump`): 74 `php` command
lines (45 × `artisan …`), 46 static PHP callables
(`Illuminate\Foundation\ComposerScripts::postAutoloadDump`,
`App\Console\Installer::postInstall`), 24 `@aliases`, 9 shell commands.
The callables receive Composer's `Script\Event` — only Composer's PHP can
run them. After `vivacity install` the user has to know which events to
run, in which order, with which environment.

### Reference (Composer 2.10.3)

- `Installer::run` with `runScripts`: `COMPOSER_DEV_MODE=1|0`, then
  **`pre-install-cmd` before anything else** (before the headline and the
  lock validation); the operations (package events `pre/post-package-*`,
  per operation, with the operation as context); the dump —
  `AutoloadGenerator::dump` dispatches `pre-autoload-dump` (flag
  `optimize`), writes, dispatches `post-autoload-dump`; then
  `post-install-cmd` after the funding report. `--no-autoloader`: no dump,
  no autoload events. `dump-autoload`: `pre-autoload-dump`, write,
  `post-autoload-dump` unless `--no-scripts`.
- `composer run-script <event>`: `--dev` / `--no-dev` set the dev mode
  (default dev), `COMPOSER_DEV_MODE` set accordingly, then
  `dispatchScript($event, $devMode, $args)` — every listener of the event,
  the plugins' included (so `@auto-scripts` of Flex works), **no flags**
  (`$event->getFlags()['optimize']` absent). An event with no listener at
  all: `Script "x" is not defined in this package`, exit 1. A failing
  script: `ScriptExecutionException`, Composer exits with the script's
  code.
- `post-root-package-install` (23 corpus projects) belongs to
  `create-project` only; never on install.

### Decision and constraints

- `vivacity install --run-scripts` (and `dump-autoload --run-scripts`):
  after each of vivacity's own phases, `composer run-script [--no-dev]
  <event>` for each event **declared in `composer.json` `scripts`**, in
  `Installer::run`'s order: `pre-install-cmd` (before the headline),
  `pre-autoload-dump`, `post-autoload-dump` (around the dump, skipped with
  `--no-autoloader`), `post-install-cmd` (after the funding lines). Working
  directory `-d <project>`, stdout/stderr inherited (Composer's `> ` lines
  appear as they do), `--no-interaction`, `--no-ansi` only when vivacity's
  own stderr is not a TTY. The first non-zero exit stops the run with that
  code, like Composer.
- Not reproducible, documented: the package events (`pre/post-package-*`,
  5 corpus projects; `run-script` cannot carry an operation) and the
  `optimize` flag of the autoload events.
- Plugin listeners of those events run again through `run-script` (they
  are Composer's, idempotent for the emulated ones — CodeSniffer.conf,
  GeneratedConfig.php rewrite the same bytes); documented.
- The Composer fallback with `--run-scripts` drops `--no-scripts`:
  Composer then runs everything itself, in its own order.
- `composer` absent with `--run-scripts` and at least one declared event:
  error before any phase (`composer not found: --run-scripts needs it`),
  exit 3, nothing written.
- Without the flag nothing changes (byte-identical harnesses untouched).

### Non-goals

`update --run-scripts` (the update's events are `pre/post-update-cmd`,
the same mechanism, a later plan once `update` is exercised with plugins),
`require`/`remove`, `create-project`, per-package events.

### Success criteria (observable)

1. Fixture `fixtures/projects/scripts`: a lock of two small packages, and
   `scripts` for the four events that append a line
   `<event> dev=<COMPOSER_DEV_MODE> n=<counter>` to `scripts.log` via
   `@php -r`, plus a static callable class under `autoload` for
   `post-autoload-dump` (proves the autoloader is usable at that point),
   plus an `@alias`. `harness/scripts.sh`: `composer install` (scripts on)
   against `vivacity install --run-scripts`, then `dump-autoload -o` both
   with scripts, then `install --no-dev`: `scripts.log` identical (order,
   dev flag, counters), `vendor/` identical, exit codes identical; a
   variant whose `post-install-cmd` exits 7: both exit 7; a variant with
   `--no-autoloader`: no autoload events on either side. In `ci.yml`.
2. `vivacity install` without the flag: `steps.sh`, `diff-vendor.sh`
   unchanged.
3. Docs: README (Plugins and scripts: the flag, the order, what it
   cannot carry), CHANGELOG, HANDOVER, DECISIONS, CONTRIBUTING, this plan.

## 2. Plan

1. `crates/vivacity/src/scripts.rs` (new): `declared_events(manifest) ->
   BTreeSet<&str>`; `run_event(project, event, with_dev, composer) ->
   Result<i32>` (spawn `composer run-script`, inherit stdio, `-d`,

   -> Option<PathBuf>` (`which_composer`).

   `dump_autoload` (not with `--no-autoloader`); `post-install-cmd` after
   `print_funding`; fallback: no `--no-scripts` when `--run-scripts`.
   `run_dump`: the two autoload events. Each non-zero code returns at
   once.
3. Fixture + harness + `ci.yml` step.
4. Docs.

### Meta (self-checklist, level 1)

- Order verified in the source (Installer.php:309-315, 375-441;
  AutoloadGenerator.php:198-206, 475-479); `pre-install-cmd` really runs
  before the lock check — a failing `pre-install-cmd` must abort before
  vivacity writes anything: run it before the layout/scope phase too.
- `run-script` on an undeclared event fails: gate on `scripts` keys, not
  on the event list.
- `COMPOSER_DEV_MODE`: set by `run-script` itself from `--no-dev`; do not
  set it in vivacity's environment (a stale value would leak into `php`).
- Stdout of the scripts must reach the user: inherit, never capture.
- A script may modify `vendor/` (ide-helper, `package:discover` writes
  `bootstrap/cache/*.php` outside vendor): the harness compares after the
  scripts on both sides — the fixture's scripts write outside `vendor/`
  only, so the comparison stays meaningful.
- Windows: `composer.bat` resolution is `which_composer`'s; the harness
  runs on Linux/macOS; `.bat` not in scope.
- Risk accepted: plugin listeners re-run through `run-script` (documented).

- 2026-09-17: `scripts.rs` (Runner: declared events, `composer
  run-script --no-interaction -d <project> [--no-dev] <event>`, stdio
  inherited, exit code returned); `--run-scripts` on `install` and
  `dump-autoload`; four dispatch points in `run_install` (the

  expansion) and two static callables reading `getFlags()` and the local
  repository. Harness 4/4: 15 log lines identical (dev, `dump -o`,
  `--no-dev`), exit 7 propagated with `post-install-cmd` never run,
  `--no-autoloader` without autoload events, nothing without the flag.
  Measured divergence: `optimize=0` under Composer, absent under
  `run-script` — normalised by the harness, documented.
