# Le cache de la sonde de plateforme ne voit pas les bibliothèques — cadrage + plan, révision 2

> Révision 2 (2026-10-09) après une méta adversariale menée sur le code : douze
> défauts, dont deux critiques vérifiés ici. §7 est la conception retenue ; §3 et
> §4 restent pour la trace de ce qui a été réfuté.

> Known issue publiée avec la 0.20.0. Niveau 2 : les versions `lib-*` / `ext-*`
> sont des **entrées de la résolution**, un cache faux donne un lock faux.

## 1. Le fait

`platform::probe()` (`vivacity-resolver/src/platform.rs`) met en cache la sortie
de `assets/platform-probe.php`, une transcription de
`PlatformRepository::initialize()`. Clé actuelle : le binaire PHP (chemin, mtime,
taille), chaque `.ini` chargé ou scanné et le répertoire de scan, et `PHPRC`,
`PHP_INI_SCAN_DIR`, `XDEBUG_MODE`, `XDEBUG_CONFIG`.

Mesuré le 2026-10-08 : `brew` a monté pcre2 de 10.47 à 10.49. PHP n'a pas bougé
(même binaire 8.5.10) mais charge la nouvelle bibliothèque et répond
`PCRE_VERSION = 10.49` ; vivacity a continué de servir `lib-pcre 10.47` et
`lib-pcre-unicode 16.0.0` (Composer : `17.0.0`). Trois oracles du résolveur
sont tombés en local, verts en CI (cache neuf).

Ce que la clé ignore, donc :
1. **les bibliothèques partagées que le binaire charge** (pcre2, icu, libxml2,
   openssl, curl, zlib…) — elles alimentent la plupart des `lib-*` ;
2. **les extensions partagées** (`extension=redis` dans un `.ini` : le `.ini` ne
   bouge pas quand `pecl upgrade redis` remplace `redis.so`) — `ext-*` ;
3. **les bibliothèques des extensions** (`intl.so` charge icu) — `lib-icu`.

Contournement publié : supprimer `platform-probe.json`.

## 2. Mesures préalables (sondes, cette machine, Homebrew)

- `DYLD_PRINT_LIBRARIES=1 php -r ''` imprime **chaque image chargée**, binaire,
  bibliothèques, extensions et leurs dépendances transitives, sur stderr, **sans
  coût mesurable** (30 ms avec ou sans). Sur la sonde qui tourne de toute façon
  quand le cache rate, c'est gratuit.
- Mais **903 images**, dont l'écrasante majorité vient de `/usr/lib` et
  `/System/Library` : elles vivent dans le cache partagé de dyld et n'existent
  pas comme fichiers (un `stat` échoue).
- Et le **piège principal** : dyld imprime le chemin **résolu**
  (`/opt/homebrew/Cellar/pcre2/10.49/lib/libpcre2-8.0.dylib`). Homebrew garde
  l'ancien keg après une mise à jour — mesuré : `Cellar/pcre2/10.47_1` et
  `Cellar/pcre2/10.49` coexistent, seul le lien `opt/pcre2` change de cible.
  Une clé faite de chemins résolus + `stat` aurait donc été **toujours valide
  après la mise à jour** : l'ancien fichier n'a pas bougé. Il faut une clé qui
  voie le **repointage**, pas seulement le contenu.
- `/opt/homebrew/opt` a bien changé de mtime au moment de la mise à jour
  (2026-10-07 20:00, l'heure du `brew upgrade`).

## 3. Les conceptions envisagées

**C1 — Chemins résolus des images + `stat`.** Linux : `/proc/self/maps` lu par
la sonde elle-même (exact, zéro processus). macOS : `DYLD_PRINT_LIBRARIES`.
Windows : rien d'équivalent. **Réfuté par la mesure de §2** pour Homebrew (keg
conservé) ; juste sous apt/dnf, qui remplacent les fichiers en place.

**C2 — Noms d'installation (`otool -L`, `ldd`) re-résolus à chaque contrôle.**
Exact sur le repointage. Coûts : `otool` exige les Command Line Tools (pas
garantis), la récursion sur les extensions est à écrire, et `ldd` exécute du
code de l'objet inspecté sur certaines glibc — à ne pas faire sur un chemin
chaud.

**C3 — Marqueurs de gestionnaire de paquets.** Toute opération Homebrew
réécrit `<prefix>/opt` ; dpkg réécrit `/var/lib/dpkg/status`, rpm sa base,
apk `/lib/apk/db/installed`, pacman `/var/lib/pacman/local`. Un `stat` de
chacun de ceux qui existent ; le préfixe Homebrew se déduit des images
(`…/Cellar/<nom>/<ver>/…`). Grossier : un `brew install` sans rapport
re-sonde (30 ms, une fois). Aveugle à une bibliothèque remplacée **hors**
gestionnaire.

**Retenu : C1 + C3**, chacun couvrant le trou de l'autre :
- les images **qui existent sur disque** (on écarte le cache partagé de dyld),
  avec leur identité de fichier (mtime, taille, et inode sur unix) → couvre un
  remplacement en place, y compris hors gestionnaire ;
- les marqueurs de gestionnaire → couvrent le repointage (le cas mesuré) ;
- la version du système (`kern.osversion` sur macOS, ou le mtime de
  `/System/Library/CoreServices/SystemVersion.plist`) → couvre le cache partagé
  de dyld, que seule une mise à jour du système modifie ;
- Windows : les DLL du répertoire de `php.exe` et de `extension_dir`, faute de
  liste des images — la distribution Windows de PHP embarque ses DLL là.
- Et la clé actuelle (binaire, `.ini`, environnement) reste.

## 4. Étapes

- **E0 — test rouge d'abord.** Un test qui reproduit le défaut **sans
  Homebrew** : un faux `php` (script) qui lit sa version de bibliothèque dans un
  fichier, une « bibliothèque » repointée par lien symbolique entre deux
  cibles, un marqueur qui change — et qui montre aujourd'hui une valeur périmée.
  Vu rouge sur `main`.
- **E1 — la sonde rapporte ses images.** `platform-probe.php` ajoute une entrée
  `{"kind": "images", "paths": [...]}` lue de `/proc/self/maps` quand il existe ;
  côté Rust, `run_probe` pose `DYLD_PRINT_LIBRARIES=1` sous macOS et lit
  stderr. L'entrée `images` est retirée de ce qui part vers
  `platform_packages` : elle sert la clé, pas la résolution.
- **E2 — la clé.** `ProbeCache` gagne `images: Vec<FileId>` (filtrées sur
  l'existence), `markers: Vec<FileId>`, `os: Option<String>`. Le format du
  fichier change : un cache de l'ancien format **ne valide jamais** (il est
  relu, la désérialisation échoue, il est réécrit) — à vérifier, pas supposer.
- **E3 — coût.** Le chemin rapide devient N `stat` (N ≈ images sur disque +
  marqueurs). À **mesurer** sur Laravel no-op avant/après, `hyperfine`, et à
  comparer au budget : la sonde coûte 30-60 ms, le chemin rapide doit rester
  sous ~1 ms.
- **E4 — doc.** DECISIONS (la mesure du keg conservé, le choix C1+C3, ce qui
  reste aveugle), CHANGELOG (Fixed + retrait de la Known issue), HANDOVER, et
  `VIVACITY_NO_PLATFORM_CACHE` rappelé comme échappatoire.

## 5. Ce qui restera aveugle, à écrire

- une bibliothèque remplacée hors gestionnaire **et** repointée par lien sans
  toucher au fichier précédent (les deux à la fois) ;
- sous Windows, une DLL chargée depuis le `PATH` hors des deux répertoires.

## 6. Non-objectifs

- Supprimer le cache : 30-60 ms par install, la majeure partie d'un no-op.
- Un TTL : écarté par principe dans ce projet (DECISIONS 2026-09-19), et il ne
  corrige pas la péremption, il la borne.

## 7. Révision 2 — ce que la méta a réfuté, vérifié ici, et la conception retenue

Vérifié moi-même avant d'écrire :
- **un wrapper `#!/bin/sh exec php "$@"` donne 0 image** (SIP efface `DYLD_*` en
  passant par `/bin/sh`), alors que la sonde, elle, voit le vrai binaire
  (`realpath(PHP_BINARY)` = `/opt/homebrew/Cellar/php/8.5.10/bin/php`). Le plan
  r1 déduisait le préfixe Homebrew des images : sans image, pas de marqueur, et
  **le bug restait intact** derrière n'importe quel wrapper, shim ou alias ;
- **`Probed` exige `name` et `version`** (platform.rs:41) : une entrée
  `kind: images` dans la sortie cassait `platform_packages` — dès le second run,
  via le cache ;
- **`install` fait `probe().ok()`** (lib.rs:839) : toute nouvelle erreur de la
  sonde serait devenue « pas de PHP », contrôle de plateforme sauté en silence ;
- **`COMPOSER_ALLOW_XDEBUG` est lu par la sonde mais absent de `PROBE_ENV`** :
  un défaut déjà présent.

### Conception retenue : ne cacher que ce qu'on voit, sinon ne pas cacher

1. **La sonde rapporte ses propres faits** à côté de ses entrées, dans un objet
   `{"entries", "binary", "ext_dir", "maps"}` : `realpath(PHP_BINARY)`,
   `extension_dir`, et sous Linux les fichiers de `/proc/self/maps` lus **en
   dernier** (fichiers ordinaires, dédupliqués, le script de sonde exclu ; un
   mapping ` (deleted)` rend la liste inutilisable). Sous macOS, les images
   viennent de `DYLD_PRINT_LIBRARIES` sur stderr, lignes dyld retirées de tout
   message d'erreur. Sous Windows, les DLL du répertoire de `PHP_BINARY` et de
   `extension_dir`, lues par `read_dir` (les métadonnées viennent avec
   l'entrée). **Rien de tout ça n'entre dans `probed`.**
2. **Règle d'échec fermé** : le cache n'est écrit que si `binary` est le php
   localisé et canonicalisé **et**, sous unix, si des images ont été vues. Sinon
   la sonde tourne à chaque fois, sans erreur — un lock faux coûte plus cher que
   40 ms. C'est la règle que le code applique déjà quand `locate_php` échoue.
3. **La clé** : un numéro de format **comparé** (pas un échec de désérialisation
   accidentel) et le texte de la sonde ; le binaire, les `.ini` et chaque image,
   avec mtime, taille, **ctime et inode** sous unix ; l'environnement, élargi à
   `COMPOSER_ALLOW_XDEBUG`, `LD_LIBRARY_PATH`, `LD_PRELOAD`,
   `DYLD_LIBRARY_PATH`, `DYLD_FALLBACK_LIBRARY_PATH`, `DYLD_INSERT_LIBRARIES` ;
   pour chaque image `<prefix>/Cellar/<formule>/…`, la **cible du lien
   `<prefix>/opt/<formule>`** — exact sur le repointage mesuré, sans
   invalidation par un `brew install` sans rapport ; et les marqueurs système
   qui existent : `/etc/ld.so.cache`, les bases dpkg / rpm / apk / pacman (pour
   les fichiers de données — tzdata, ICU — qu'aucune liste d'images ne voit),
   et le fichier du cache partagé de dyld (plutôt que la version du système).
4. **Course** : les marqueurs et liens sont relevés avant et après la sonde ;
   s'ils diffèrent, rien n'est écrit.

### Tests

- (a) une couture `probe_at(php, cache_file)` et un faux `php` qui émet la
  sortie au nouveau format et, sur stderr, des lignes au format dyld nommant des
  fichiers d'un arbre `Cellar/pcre2/{a,b}` avec un lien `opt/pcre2` : repointer
  le lien et changer la version annoncée **doit** relancer la sonde. Rouge sur
  `main`, dont la clé ne voit que le faux php ;
- (b) un wrapper `#!/bin/sh` autour du vrai php qui compte ses lancements : deux
  `probe_at` → deux lancements (échec fermé) ;
- (c) le vrai php : les images contiennent `realpath(PHP_BINARY)` et une
  `libpcre2` ;
- (d) sentinelle : la sonde en cache égale la sonde sans cache.

### Ce qui reste aveugle (à écrire)

Une bibliothèque remplacée hors gestionnaire en conservant mtime, taille,
ctime et inode (impossible sans privilèges) ; une DLL Windows chargée depuis le
`PATH` hors des deux répertoires ; un shim qui choisit un autre php selon le
répertoire courant — couvert par la règle 2 dès que ce php n'est pas le
binaire localisé.

## 8. Issue

Livré tel que la révision 2 le décrit. Mesures et décisions : DECISIONS
2026-10-09. Coût du chemin chaud : ~0,4 ms de plus que la clé de la 0.20.0 ;
sans cache : ~45 ms.
