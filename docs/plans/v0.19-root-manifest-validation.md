# Validation du manifeste racine

> Révision 2 (2026-09-28), après une méta adversariale menée par un relecteur
> frais **avec accès au dépôt**. Elle a réfuté quatre points de la révision 1 ;
> la §6 les liste. Le cadrage tient, la forme change.

## 1. Cadrage

### Problème
Sur un manifeste que Composer **refuse**, vivacity réussit : `exit 0`, un lock
écrit, un autoloader posé. Mesuré le 2026-09-28, chaque ligne étant Composer
`exit 1` contre vivacity `exit 0` :

| manifeste | Composer refuse dans |
|---|---|
| `"require": {"Symfony/Flex": "^2"}` | `RootPackageLoader` (nom de lien) |
| `"name": "vivace/wordpress.json"` | `RootPackageLoader` (nom racine) |
| `"require": {"x/y": "not a constraint"}` | `ArrayLoader` + `VersionParser` |
| `"require": {"x/y": "^2 as bogus"}` | `VersionParser` |
| `"require": {"symfony/flex": []}` | schéma JSON |
| `"minimum-stability": "bogus"` | schéma JSON |
| `"version": "not.a.version"` | schéma JSON |
| `repositories[]` sans `type` / `type` inconnu | schéma JSON |

C'est le **premier écart de ce sens** du projet : ailleurs vivacity rend la
main quand il ne sait pas reproduire ; ici il produit un résultat là où la
référence refuse d'en produire un.

### Ce que la méta a changé au diagnostic
Le défaut n'est **pas** « des règles manquent » : il est **architectural**. Le
refus des alias malformés est déjà porté (`crates/vivacity-resolver/src/root.rs`)
et `dump-autoload` l'accepte quand même, parce que chaque commande charge le
manifeste à sa façon et que seule `update` passe par le chargeur racine du
résolveur. « Déjà porté » n'est pas « appliqué à chaque point d'entrée ».

De même, `ValidatingArrayLoader::hasPackageNamingError` est **déjà porté**
(`crates/vivacity-resolver/src/lockfile.rs:715`, `package_naming_error`), mais
seulement dans sa branche `$isLink = false`, appelée depuis `validate_package`
— et sa suggestion de nom est fausse (voir §3.2).

### Décision : refus natif, texte seul, code identique
Pas de reproduction à l'octet, pas de délégation. La maison a déjà tranché ce
cas et l'a écrit — `HANDOVER.md`, dépôts `path` : « la forme encadrée des
erreurs (`In PathRepository.php line 163:` + synopsis — vivacity imprime le
texte seul, code identique) ». On suit.

Pourquoi pas la reproduction à l'octet, mesuré : l'encadré de Symfony Console
est **replié à la largeur du terminal** (`COLUMNS=40` → 39 colonnes,
`COLUMNS=200` → 113, coupant les mots), il est suivi du **synopsis de la
commande**, et il peut être **chaîné** (deux encadrés pour une contrainte
invalide). Le numéro de ligne du phar n'est que l'argument le plus faible.

Pourquoi pas la délégation : `run_dump` n'a aucun chemin de délégation (il rend
3, Composer rend 1) ; `fallback_or_fail` exigerait une variante de `ScopeIssue`
et un en-tête (« outside what vivacity handles natively ») qui décrit mal un
manifeste que la référence refuse aussi ; et **sans Composer sur le `PATH` la
délégation rend 3** — précisément le cas de l'utilisateur du binaire autonome.

### Non-objectifs, mesurés et non devinés
- **La famille du schéma JSON** (5 des 8 refus du tableau). Détecter suffirait
  (un booléen) et `res/composer-schema.json` est dans le phar (90 886 octets,
  draft-04), mais un refus **natif** exige le texte de `justinrainbow/json-schema`,
  et le projet épingle ses versions sans porter de validateur JSON Schema.
  Reporté ; l'écart est écrit tel qu'il est mesuré, cinq contre trois.
- **La contrainte invalide** (`ArrayLoader` + `VersionParser`). Mesurée : deux
  encadrés chaînés, `Link constraint in <racine> requires > <cible> should be a
  valid version constraint, got "<contrainte>"` puis `Could not parse version
  constraint <morceau>: Invalid version string "<morceau>"`. Reportée parce
  qu'elle exige en plus que le texte d'erreur de notre parseur de versions
  corresponde — une autre question de portage, pas celle-ci.
- La forme encadrée, le repli à la largeur du terminal, le synopsis.

### Ce qui fait l'unité de ce changement
Le **point de passage** (les cinq commandes, avant toute écriture) plus la
**famille des noms** (une seule fonction, une seule forme de message). Les
familles reportées s'y branchent ensuite en quelques lignes : c'est le point
de passage qui est le livrable qui généralise.

### Critères de succès observables
1. Pour chaque cas du banc : même code de sortie que Composer (**1**), le texte
   du message identique, et **rien d'écrit** — vérifié contre une copie
   intacte par mtime, pas par `compare_vendor` (qui ne compare pas les mtimes :
   mesuré, `dump-autoload` laisse l'empreinte de l'arbre inchangée tout en
   écrivant l'autoloader).
2. Chaque cas vu **rouge** avant le changement. Attention au bon rouge : sur un
   projet verrouillé, ajouter une exigence rend le lock périmé, donc la
   référence de `install` est `exit 4` « Required package … is not present in
   the lock file », pas `exit 0`. Le garde doit donc être **avant** le contrôle
   de péremption du lock.
3. Les cinq commandes couvertes : `install`, `dump-autoload`, `update`,
   `remove`, `require` — et pour `require`/`remove`, **avant** la réécriture de
   `composer.json` (sinon `files.revert()` imprime « Installation failed,
   reverting ./composer.json to its original content. », que Composer
   n'imprime jamais ici).
4. Toute la suite de bancs reste verte : aucun manifeste réel ne déclenche le
   garde. La méta l'a déjà vérifié à l'oracle sur 141 manifestes racines,
   4 806 noms de liens et 16 236 noms du lock : zéro erreur.
5. Le test oracle contre le phar pointe sur la fonction **existante**.

## 2. Les règles portées, lues dans la source (Composer 2.10.3)

Toutes dans `RootPackageLoader::load`, dans cet ordre :

1. **Nom racine.** `if (!isset($config['name'])) { $config['name'] = '__root__'; }
   elseif ($err = hasPackageNamingError($config['name'])) { throw 'Your package
   name '.$err; }` — branche `$isLink = false`.
2. **Auto-exigence.** Pour `require` puis `require-dev`, si les cibles
   contiennent `$config['name']` → « Root package '%s' cannot require itself in
   its composer.json » + seconde ligne. Déjà porté (`root.rs:131`), à appliquer
   partout. Inatteignable avec un nom racine en majuscules, qui lève avant.
3. **Nom de chaque lien.** Pour les cinq types de
   `BasePackage::$supportedLinkTypes` — `require`, `conflict`, `provide`,
   `replace`, `require-dev` — chaque clé par `hasPackageNamingError($name, true)`,
   première erreur levée comme `$linkType.'.'.$err`.
4. **Alias malformé.** Déjà porté (`root.rs:264`), à appliquer partout.

`hasPackageNamingError(name, isLink)`, dans l'ordre : paquet de plateforme
exempté ; motif éditeur/paquet ; noms de périphériques Windows réservés (21,
après `strtolower`, éditeur **ou** paquet) ; suffixe `.json` ; majuscules — avec
`Please use <minuscules> instead` si `isLink`, sinon `We suggest using
<camelCase éclaté> instead`.

### Le motif et son moteur
Le port existant utilise PCRE2 avec le motif **verbatim sauf `$` → `\z`**, et
c'est le bon choix, pour une raison que la révision 1 avait fausse :
- le `RegexBuilder` embarqué n'expose **pas** `DOLLAR_ENDONLY`, donc le `D` de
  PHP ne peut pas être passé — `\z` le remplace, et c'est déjà ce que font
  `lockfile.rs:722` et `platform.rs:34` ;
- les quantificateurs possessifs sont **sans effet ici** : la méta l'a mesuré en
  force brute côté PHP, 597 870 sujets sur l'alphabet `{a,0,.,_,-,/,\n,A,z}`
  jusqu'à six caractères, zéro divergence ;
- la vraie raison de garder PCRE2 est le **repli de casse ASCII** : `(?i)[a-z0-9]`
  dans le moteur `regex` de Rust applique le repli Unicode simple, donc
  `ſymfony/flex` (U+017F) passerait, là où PCRE2 sans UTF ne replie que des
  octets ASCII et Composer refuse. Mesuré des deux côtés.

## 3. Plan

1. **Généraliser** `lockfile.rs::package_naming_error(name)` en
   `package_naming_error(name, is_link)` et la rendre accessible aux deux
   appelants (module partagé du crate résolveur). Une seule implémentation.
2. **Corriger la suggestion de nom** de la branche `is_link = false`, qui est
   aujourd'hui un `to_lowercase()` plat là où PHP éclate le camelCase :
   `Preg::replace('{(?:([a-z])([A-Z])|([A-Z])([A-Z][a-z]))}', '\1\3-\2\4', $name)`
   puis `strtolower`. Oracle : `Foo/BarBaz` → `foo/bar-baz` (Composer) contre
   `foo/barbaz` (nous), `a/bC` → `a/b-c`. Bug présent dans le chemin
   `validate_package` livré, trouvé par la méta.
3. **`root_manifest_error(manifest) -> Option<String>`** dans `root.rs` : les
   quatre règles de §2 dans l'ordre de Composer, renvoyant le message **tel
   quel**, préfixes compris.
4. **Le point de passage** : appelé par les cinq commandes, à leur propre
   lecture du manifeste, avant toute écriture — `run_install` (~591),
   `run_dump` (~1845), `resolve_and_lock` (~3219), `run_remove` (~3764),
   `require::run_require` (~344). Refus natif : message sur stderr, `exit 1`,
   rien d'écrit.
5. **Banc** : une ligne par règle dans `harness/steps.sh` via la préparation
   `@jq:` existante (qui compare déjà les codes de sortie, `composer.json` et
   `composer.lock` octet à octet, et filtre `^vivacity: `), **plus** des cas
   `dump-autoload` là où `steps.sh` n'en a pas. Deux pièges relevés par la
   méta : la comparaison de stderr de `steps.sh` est **ancrée** sur une liste de
   débuts de ligne qu'aucun encadré d'erreur ne satisfait — ajouter une
   alternative `^In [A-Za-z]+\.php line ` ou assumer `@nostderr` (et alors le
   dire : « même stderr » ne serait vérifié nulle part) ; et « rien d'écrit » se
   vérifie par mtime contre une copie intacte.
6. **Drift** : `docs/reference/` n'a pas `ValidatingArrayLoader.php` et la table
   `twin()` de `harness/drift-reference.sh` n'a pas son entrée — les règles de
   nommage déjà livrées ne sont surveillées par rien. À ajouter.
7. **Doc** : README (ce qui est refusé, ce qui ne l'est pas, avec le compte
   mesuré), DECISIONS, CHANGELOG, HANDOVER.

## 4. Vérification
- Chaque cas du banc vu rouge avant, avec le bon rouge (§1, critère 2).
- Suite complète : steps, diff-vendor, update, flex-*, removal, path-repos,
  transitions, boot, vendor-dir.
- Oracle sur la fonction existante, sur le corpus de noms fabriqués **et** sur
  tous les noms de liens des fixtures.
- Revue indépendante obligatoire (niveau 2) à la fin.

## 5. Risques résiduels assumés
- Le refus natif imprime le texte sans l'encadré : déviation déjà documentée
  pour les dépôts `path`, étendue ici. À écrire dans HANDOVER.
- Les familles schéma et contrainte restent ouvertes, donc « validation du
  manifeste racine » ne signifie pas « tout ce que Composer refuse » : trois
  refus sur huit du tableau de §1. Le dire dans le README plutôt que de laisser
  croire l'inverse.
- `fallback_or_fail` ne transmet pas `--dry-run` à Composer (bug latent hérité,
  hors périmètre) : sans objet ici puisqu'on ne délègue pas.

## 6. Ce que la méta a réfuté de la révision 1
1. « Ajouter `naming_error` dans `root.rs` » — la fonction existe déjà dans
   `lockfile.rs`. La révision 1 aurait écrit une **seconde** copie de la même
   fonction de Composer dans le même crate.
2. « Le `name` de la racine est validé par le schéma, pas par le chargeur » —
   faux : le chargeur le valide, avec la branche `$isLink = false` que la
   révision 1 mettait hors périmètre. Et cette branche porte un bug.
3. « Trois points d'entrée » — il y en a **cinq**, et `require`/`remove`
   écrivent `composer.json` avant le site que la révision 1 visait.
4. « Router par le chemin de délégation existant » — `run_dump` n'en a pas,
   `fallback_or_fail` exige une variante de `ScopeIssue` inexistante, et la
   délégation dépend de Composer sur le `PATH`. La reproduction native est la
   forme déjà retenue ailleurs dans le projet.

Retenus aussi : le nouveau banc dédié est inutile (`steps.sh` fait déjà tout,
une ligne par règle), le piège de l'ancre de stderr, l'impossibilité de
vérifier « rien d'écrit » par `compare_vendor`, et le bon rouge de `install`.
