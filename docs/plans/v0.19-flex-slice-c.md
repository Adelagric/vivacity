# v0.19 — Flex slice C: `update` with install, in general

## 1. Scope

### Where slice B stopped
`update` with install is native on a Flex project only when the install
lays out **nothing new**: that is the one case where every package Flex
records is already extracted at the version the new lock names, so both
questions — does the recipe index have an entry, does the package ship a
bundle class — are answerable before anything is written.

Measured after B (2026-09-23/24):
- `fixtures/work/symfony`, steady state: 123 of 153 packages are absent
  from `symfony.lock`; none has a recipe, none a bundle class → native.
- `fixtures/work/sylius`, steady state: 213 of 276 absent, and one —
  `nyholm/psr7` 1.8.2, recipe at `1.0` — does have a recipe → hand-over,
  correctly. 5 packages are typed `sylius-plugin` (the second branch of
  `extractClassNames`, ported and unit-tested).
So B covers "nothing changed" and nothing else. Every real update — the
reason one runs the command — still goes to Composer.

### What C has to add
1. **The bundle question for a package being installed or updated.**
   `SymfonyBundle::isBundleClass` reads
   `vendor/<name>/<path>/<Class>.php` and looks for two literal needles.
   At `POST_UPDATE_CMD` the file is there; before the install it is not.
   vivacity holds the dist in its store (or its cache) before extracting,
   so the candidate file can be read out of the archive — zip and tar
   extractors already exist (`vivacity-core::extract`).
2. **The `symfony/thanks` reminder.** `Flex::activate` arms it for the
   `update` command; `POST_PACKAGE_UPDATE` promotes it to 2 when
   `symfony/thanks` is not installed; `install()` then prints three lines
   (one blank, two text, with `💖 `/`★ ` and their trailing spaces). It
   fires on any version bump — i.e. on nearly every real update.
3. **Removals.** `getClassNames()` with `$uninstall = true` skips
   `isBundleClass` entirely and returns every candidate name, so a
   removal almost always yields an auto-generated recipe → `Symfony
   operations: N recipe(s)`, `- Unconfiguring …`, and
   `config/bundles.php` rewritten. Any transaction with a removal must
   hand over.
4. **symfony.lock.** With a recipe-less install of a package absent from
   the file, `fetchRecipes` writes nothing for it; with an
   auto-generated bundle recipe it does `lock->set(name, {version})`.
   C must keep the file byte-identical or hand over.

### Non-goals
The fourteen configurators, recipes that apply, `--reset`,
`recipe-conflicts` (still ignored: it only removes index entries, so the
error direction stays "needless hand-over").

### Success criteria
1. `harness/flex-update.sh` gains cases where the transaction is NOT
   empty: a package installed that has no recipe and no bundle (native,
   project and symfony.lock identical), one that has a bundle class in
   its archive (hand-over, nothing written), one updated (the thanks
   reminder printed identically), one removed (hand-over).
2. The archive read is proven against the extracted file: for every
   package of the symfony and sylius fixtures, the answer from the
   archive equals the answer from vendor/.
3. `harness/update.sh` and `flex-install.sh` unchanged.

## 2. Meta-analysis (fresh reviewer, before executing)

Verdict: the slice as first cut spent its budget on the wrong third.

1. **The archive read is the least valuable item.** It only matters for a
   package that is *both* absent from `symfony.lock` *and* recipe-less
   *and* a bundle — and in that case the answer is "hand over" anyway.
   Reading the dist buys a *native* run only for packages that ship no
   bundle, which the recipe index already filters. It also forces a
   decision we have not written down: dists are fetched *after* the lock
   is written, so answering before the write means fetching earlier.
2. **The real blocker is our own `flex_write_guard`.** Its
   `package.json` / `importmap.php` clause hands over on *every* real
   Symfony application, whatever the transaction. Narrowing it is pure
   lock/stat work and frees projects that today delegate for nothing.
3. **Slice B's precondition is too coarse.** "The install lays out
   nothing new" is a whole-transaction verdict; Flex asks its questions
   *per package*. The per-package form needs the transaction hoisted
   above the lock write, which is the same move the gate already made.
4. Success criterion 2 ("for every package of the symfony and sylius
   fixtures, the archive answer equals the vendor answer") is vacuous as
   long as those fixtures hold no bundle-shipping package absent from
   `symfony.lock`: it would pass on `false == false`. It is replaced by
   hand-built-archive unit tests plus positive assertions on packages
   that really do ship a bundle.
5. Every flex measurement so far was taken on a `stage_project` shape
   that omits `importmap.php`, `package.json` and `assets/` — so the
   guard above never fired in the harness, and its cost was invisible.

### Re-cut order
1. Narrow `flex_write_guard`'s `package.json` / `importmap.php` clause.
2. The `symfony/thanks` reminder, with the predicate measured rather
   than assumed.
3. Per-package answers in place of B's global precondition.
4. Only then the archive read, tri-state (`Yes`/`No`/`CannotTell`, hand
   over on `CannotTell`), with the fetch-order decision written down and
   `dist.type == "path"` read from the source directory.

## 3. Item 1 — what `synchronizePackageJson` actually writes

Read from `symfony/flex` 2.9.x and Composer 2.10.3 (2026-09-24), not
from memory:

- `Flex::finish()` — and so `synchronizePackageJson()` — is reached only
  when the event is `POST_UPDATE_CMD` (`Flex::install`, line 427). A
  plain `install` never synchronises anything.
- `shouldSynchronize()` is `package.json || importmap.php`. That is the
  whole of today's guard, and it is far wider than what gets written.
- `importmap.php` wins when both exist: `synchronizeForAssetMapper()`
  returns `false` always, calls `updateImportMap()` — which returns
  before touching the file when the entry list is empty — and
  `updateControllersJsonFile()` — which returns immediately when
  `assets/controllers.json` is absent. Entries come from
  `resolveImportMapPackages()`, which yields nothing unless the PHP
  package carries the `symfony-ux` keyword. **Keywords are in the lock**:
  `fixtures/projects/symfony` has 4 such packages, sylius 5,
  `fixtures/corpus/symfony-demo` 4.
- `package.json` branch, in order: an unparsable file returns `false`
  before any write; then `removeObsoletePackageJsonLinks()`, which
  **writes unconditionally**, even with nothing removed; then
  `registerDependenciesInPackageJson()`, which compares contents before
  writing; then `updateControllersJsonFile()`.
- That unconditional write is not a no-op in general.
  `JsonManipulator::__construct` does `trim($contents)` and
  `getContents()` returns `$this->contents . $newline`, where `$newline`
  is `\r\n` when the original holds one anywhere. So Composer rewrites
  `package.json` as `trim(bytes) + newline`; the bytes only survive when
  they already have that shape.
- `Flex.php:578`: the three stderr lines (`Synchronizing package.json
  with PHP packages`, the `npm install --force` warning, a blank) are
  printed only when `synchronize()` returns true — i.e. only from the
  `package.json` branch, and only on a real change.

### The honest predicate
Nothing is written, and nothing printed, when:

- `importmap.php` exists: no locked package carries the `symfony-ux`
  keyword **and** `assets/controllers.json` is absent;
- else `package.json` exists: it does not parse *(Flex bails out first)*,
  **or** no `symfony-ux` keyword **and** no `assets/controllers.json`
  **and** no obsolete `@…: file:<vendor-dir>/…/assets` link whose
  `package.json` is gone **and** `trim(bytes) + newline == bytes`;
- neither exists: nothing to do.

A `symfony-ux` package whose own `assets/package.json` is missing yields
no entry either, but that needs a vendor read — left as a needless
hand-over, which is the safe direction.

### Where it belongs
Not in `flex_write_guard`: keywords must come from the **new** lock, and
that clause is evaluated before resolving. It moves next to
`flex_install_reason`, inside `resolve_and_lock` before the lock write —
the gate slice B already proved writes nothing when it fires.

### Outcome (2026-09-24)
Done. `flex_sync_reason` sits next to `flex_install_reason`; the clause is
gone from `flex_write_guard`; `harness/flex-update.sh` went from 5 to 11
cases, the 6 new ones red before the change. Two of them are native runs
that used to hand over: a project with `importmap.php` and one with
`package.json`, both without a `symfony-ux` package — project,
`composer.lock`, `symfony.lock` and stderr identical to Composer's. The
harness also had to be fixed: the shape files are now written **after** the
convergence update, because `--no-scripts` does not stop a plugin's event
subscribers, so the preparation was doing the synchronisation itself.

## 4. Plan (items 2-4, unchanged from the first cut except the order)
1. The thanks reminder: `symfony/thanks` not an active plugin, looked up
   locally *and* in `COMPOSER_HOME`, `cfg(windows)` glyphs, printed
   between the recipes-disabled warning and the blank line, driven by the
   *installer's* update operations.
2. Per-package answers in place of B's `unchanged_local_repository`
   precondition: hoist the transaction above the lock write.
3. `vivacity-core::extract`: read one entry by path out of a zip and a
   tar dist, same single-root strip as the extractor; tri-state answer.
4. Fixture: a transaction, obtained by pinning an older version in the
   existing snapshot, and the fixture's real 30-entry `symfony.lock`
   staged instead of a synthesised one.

### Non-goals
The fourteen configurators, recipes that apply, `--reset`,
`recipe-conflicts` (still ignored: it only removes index entries, so the
error direction stays "needless hand-over").
