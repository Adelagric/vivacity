# v0.18 — `update --with` (temporary constraints)

## 1. Scope

### Problem
Every matrix CI in the PHP world pins a dependency for the run instead of
in composer.json: `composer update --prefer-lowest --with="phpunit/phpunit:~13.3"`.
Doppar's framework repository does it in all six of its jobs; Laravel,
Symfony and Sylius do the same. vivacity refuses the form outright
("temporary constraints … are not supported yet"), so no such CI can use
it — whatever the rest of the parity is worth. The shorthand
`update foo/bar:^2` is refused with it.

### What is already there
The resolver side was ported with the solver (v0.4): `RepositorySet`
carries `temporary_constraints`, the pool builder drops every version
outside them after loading and before `PRE_POOL_CREATE`, and
`problem.rs` explains an unsolvable set in terms of them ("with your
temporary update constraint (…)"). Nothing fills the map: `session`
passes `Default::default()`, the CLI rejects the syntax.

### Reference (Composer 2.10.3, `UpdateCommand::execute`, read in the phar)
1. `$reqs = formatRequirements($input->getOption('with'))` —
   `VersionParser::parseNameVersionPairs` (`a/b:^1`, `a/b=^1`, `a/b ^1`),
   a pair without a version is an error.
2. A `packages` argument matching `{\S+[ =:]\S+}` joins `$reqs` and is
   reduced to its name in the allow list.
3. `setReferences(extractReferences($reqs, …))` and
   `setStabilityFlags(extractStabilityFlags($reqs, minimumStability, …))`
   on the root package — a temporary `dev-main#abc` or `@dev` counts.
4. Per requirement, lowercased, `parseConstraints`; a name with `*`
   expands over the root requirements through `packageNameToRegexp`.
5. Each constraint must intersect the root requirement's
   (`Intervals::haveIntersections`) — else one error line and exit 1
   (`FAILURE`), plus, outside the wildcard case, the `Run \`composer
   require …\`` hint.
6. `Installer::setTemporaryConstraints` → `RepositorySet`.

### Non-goals
`--patch-only` (it also feeds the map, from the lock) and `-i`
(interactive): separate, and neither is a CI form.

### Success criteria
1. `harness/steps.sh` cases on a snapshot fixture: `update --with`,
   the `update a/b:^1` shorthand, both forms together, a wildcard, a
   constraint disjoint from composer.json (same error, same exit code),
   a `--with` without a version — composer.json, lock, stderr and exit
   code identical to Composer.
2. `update --prefer-lowest --with=…` (Doppar's CI form) on the Doppar
   fixture: same lock as Composer, byte for byte.
3. The refusal disappears from the CLI; nothing else changes.

## 2. Plan
1. `vivacity/src/lib.rs`: `--with <REQ>` (repeatable) on `UpdateArgs`;
   drop the two refusals; a `temporary_constraints(&args, &manifest,
   &root)` helper doing steps 1–5 above, returning the map or the
   error to print.
2. `UpdateOptions.temporary_constraints`, passed to `RepositorySet::new`
   in `prepare_update`.
3. Root references and stability flags: `root.apply_temporary(&reqs)`
   next to `apply_patch`, reusing `extract_references` /
   `extract_stability_flags`.
4. Unit tests on the parsing, the wildcard expansion and the
   intersection refusals; harness cases; docs.

## 3. Meta-analysis (adversarial, self)
- **The map is keyed by package name, the filter matches `names(true)`**
  (provides and replaces included): a temporary constraint on a virtual
  name drops its providers. That is Composer's behaviour, ported as is;
  the harness case on a `provide`d name would be worth it — the snapshot
  fixtures have one (`solver-providers`).
- **Order matters**: the filter runs before the Flex filter, as in the
  PHP (`temporaryConstraints` block, then `PrePoolCreateEvent`). Already
  the case in `build_pool` — a case with both is out of reach (no Flex
  snapshot with a matrix), noted rather than tested.
- **The error is a `FAILURE` return, not an exception**: exit code 1, one
  line on stderr, nothing written. Our `anyhow::bail!` exits 1 too but
  prints `Error: …`; the message must be printed and the code returned
  by hand to match.
- **`extractStabilityFlags` on temporary requirements** can loosen the
  minimum stability for the run. Ported (step 3) because dropping it
  would silently change what resolves for `--with foo/bar:@dev`.
- **The allow list**: `update a/b:^1` must behave as `update a/b` plus
  the constraint — the name goes to the allow list, not `a/b:^1`.
- **Risk of over-reach**: `--patch-only` shares the map. Out of scope,
  and it stays refused (it is not refused today — check: it is not
  implemented either; leave as is).

## 4. Execution log
- 2026-09-22: done in one pass. CLI `--with` (repeatable) and the
  `a/b:^1` shorthand (`temporary_requirements`,
  `package_of_requirement`, the allow list taking the name alone);
  `UpdateOptions.temporary_requirements` → `session::temporary_constraints`
  (references, stability flags, wildcard expansion over the root
  requirements **in composer.json order**, `have_intersections`);
  `SessionErrorKind::Printed(code)` so a command-level refusal prints its
  message alone and returns Composer's code, with `SessionError.stdout`
  for the line Composer writes on stdout next to it;
  `pool::TemporaryConstraint` carrying the text as written, which the
  unsolvable-set explanation quotes.
  Three parity bugs the harness caught, all fixed: the explanation
  printed the compiled interval instead of `psr/log:1.1.*`; a partial
  update without a lock exited 1 with an `Error:` prefix instead of
  Composer's bare message and exit 3 (pre-existing, unrelated to `--with`);
  the wildcard reported the alphabetically first mismatching root
  requirement instead of the first in composer.json order.
  `steps.sh` gains 6 cases (laravel: `--with` pinning a root requirement,
  the shorthand, two wildcards, an unsolvable narrowing; solver-policies:
  a disjoint constraint and a disjoint wildcard — message on stderr, hint
  on stdout, exit 1), red without the change. Doppar's own CI forms
  (`update --prefer-lowest|--prefer-stable --with=phpunit/phpunit:~13.3.1`)
  produce a lock identical to Composer's, byte for byte, in both modes.
  245 tests, 240 steps cases, every harness green.
