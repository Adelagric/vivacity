# v0.13 — `wikimedia/composer-merge-plugin`, emulated without its implicit update

Started 2026-09-17. Level 2 (a plugin that rewrites the lock; a
deliberate deviation from Composer): fresh-subagent meta-analysis,
independent review.

## 1. Scope

### Problem

Four corpus projects fall back for `wikimedia/composer-merge-plugin`
(concretecms v2.0.1, invoiceninja, open-web-analytics,
salesagility-suitecrm-core v2.1.0 — same semantics), the first plugin in
the ranking after v0.11. Only **open-web-analytics** exercises the merge
today (two `modules/*/composer.json`, `require` only): invoiceninja has
no `Modules/` at its pinned commit (glob empty, plugin inert),
salesagility lists the plugin as `false` in `allow-plugins` (Composer
skips it), concretecms also carries `mlocati/composer-patcher`, leantime
declares a merge configuration but has no plugin in its lock. The fixture
therefore carries the proof; the corpus gains one entry. The plugin merges the
`composer.json` files named by `extra.merge-plugin.include` / `require`
(PHP `glob()` patterns) into the root package in memory. What that changes
on disk on an `install`: the autoloader (PSR-0/4, classmap, `files`,
`exclude-from-classmap` of the included files, paths re-based on each
file's directory) and `installed.php` (the root's `provided` / `replaced`
targets); with `merge-extra`, the root `extra` (installer paths); and the
lock validation against the root requirements.

### Reference (plugin v2.1.0, vendored under
`docs/reference/plugins/composer-merge-plugin/`, MIT)

- `MergePlugin::getSubscribedEvents`: INIT, POST_PACKAGE_INSTALL,
  POST_INSTALL_CMD, POST_UPDATE_CMD, PRE_AUTOLOAD_DUMP, PRE_INSTALL_CMD,
  PRE_UPDATE_CMD — all at priority 50000. `--no-scripts` does not silence
  them (plugin listeners run regardless).
- `PluginState::loadSettings`: defaults `include: []`, `require: []`,
  `recurse: true`, `replace: false`, `ignore-duplicates: false`,
  `merge-dev: true`, `merge-extra: false`, `merge-extra-deep: false`,
  `merge-replace: true`, `merge-scripts: false`; a string `include` is a
  one-element list. `isDevMode() = mergeDev && devMode`.
- `mergeFiles(patterns, required)`: `array_map('glob', $patterns)` — PHP
  `glob()` with **no flags** (no braces, files and directories, sorted by
  libc per pattern); a `require` pattern matching nothing throws
  `MissingFileException("merge-plugin: No files matched required '{p}'")`.
  `include` patterns first, then `require`; a path merged once is not
  merged again (`loaded` / `loadedNoDev`).
- `ExtraPackage::mergeInto`: `prependRepositories`, `mergeRequires('require')`
  (stability flags, `self.version` replaced by the root's version or
  constraint, then `mergeOrDefer`: a duplicate key is ignored
  (`ignore-duplicates`), replaced (`replace`), or **conjoined** — the
  pretty constraint becomes `"<old>, <new>"`, `Intervals::isSubsetOf`
  short-cuts to one side), `mergePackageLinks('conflict')`,
  `'replace'` (if `merge-replace`), `'provide'` (`array_merge`: the
  include wins on a duplicate key), `mergeSuggests`,
  `mergeAutoload('autoload')` (**`array_merge_recursive`** of the raw
  autoload arrays with paths prefixed by `dirname($path) . '/'` — a
  duplicate PSR-4 key yields a list of paths, lists append),
  `mergeExtra` (only with `merge-extra`; `array_merge($extra, $rootExtra)`
  — root wins — or the include wins with `replace`; `NestedArray::mergeDeep`
  with `merge-extra-deep`; `extra.merge-plugin` of the include stripped),
  `mergeScripts` (only with `merge-scripts`); then in dev mode
  `mergeDevInto`: `require-dev`, `autoload-dev`. Recursion
  (`recurse`): the include's own `extra.merge-plugin.include/require`,
  re-based on its directory, after it is merged.
- **On a bare vendor** the plugin is installed during the transaction,
  activated at once, receives POST_PACKAGE_INSTALL for itself
  (`firstInstall`), merges at PRE_AUTOLOAD_DUMP, and at POST_INSTALL_CMD
  runs `Installer::create(...)->setUpdate(true)->setUpdateAllowList(<merged
  requirement names>)` — a partial `composer update` against the live
  repositories that **rewrites composer.lock** (measured on
  open-web-analytics with its real module files: maxmind-db/reader
  1.13.1 → 1.14.0, monolog 2.11.0 → 2.11.1, symfony/filesystem 7.4.15 →
  7.4.18, +28/−27 lock lines) and installs the result. With the plugin
  already in `installed.json` (warm vendor) nothing of the sort happens:
  the merge is applied from INIT (`Factory::create` dispatches it after
  `loadInstalledPlugins`, before `Installer::create`) and the lock is
  validated against the merged requirements like any root requirement
  (`Locker::getMissingRequirementInfo`: `Required package x is not
  present in the lock file` / `… is in the lock file as "v" but that does
  not satisfy your constraint "…"`, exit 4 — **no implicit update, no
  lock rewrite**; a merged `conflict`/`replace` against a locked package
  fails the install-mode solve: `Your lock file does not contain a
  compatible set of packages`).
- Composer's own steady state is therefore: root merged, lock as
  committed, autoloader and `installed.php` from the merged root.

### Decision (2026-09-17, with the user): deterministic, never the implicit update

vivacity emulates the merge and validates the lock against the merged
requirements exactly as Composer does with the plugin already installed
(`missing_requirement_info`, the port of `getMissingRequirementInfo`,
exit 4 with the same lines); it **never** runs the plugin's implicit
partial update nor rewrites the lock during an `install`. On a bare
vendor (plugin absent from `installed.json`), where Composer would run
that update, a lock that does not satisfy the merged requirements is
handed to Composer with the reason instead. Rationale
in DECISIONS: Composer's cold-vendor result depends on the registry at
that instant — not reproducible even by Composer; at a frozen registry
its implicit update is a no-op and its output equals vivacity's, so the
parity is provable; the precedent of `pest-plugins.json` and the `files`
order (vivacity writes the deterministic form and says so).

### Constraints

- Byte-identical to Composer's steady state (warm plugin, committed lock)
  in both dev modes: autoloader (plain, `-o`, `-a`), `installed.json`,
  `installed.php`, whole project.
- Same gating as the other emulations: plugin in the lock (wanted for
  the mode), allowed by `allow-plugins`, plugins enabled; `--no-plugins`
  → no merge (Composer loads nothing).
- `vivacity update` / `require` / `remove` on a project whose
  **manifest** requires the plugin (`require`/`require-dev`), allows it
  and declares `extra.merge-plugin` are refused (gating on the lock would
  miss the first `update` of a project without a lock) — they would
  resolve without the merged requirements and repositories. Emulating the
  merge for resolution is a later plan.
- The merged `require` constraints are **structured**, not textual: a
  duplicate key without `ignore-duplicates`/`replace` is Composer's
  conjunctive `MultiConstraint` (`ExtraPackage::mergeConstraints`, with
  the `Intervals::isSubsetOf` short-cuts), pretty string `"<old>, <new>"`
  kept aside for the error line. A textual `"^2.11 || ^1.0, ^2.8"` would
  parse as `^2.11 || (^1.0, ^2.8)` — verified to accept a lock Composer
  refuses. Hence the merge of the link sections lives in
  `vivacity-resolver` (which owns `Constraint`, `Intervals`, `Link`).
- `RootPackage::detect` (branch alias, version) reads the **original**
  manifest: `RootPackageLoader` runs before INIT, so a merged
  `extra.branch-alias` never becomes a root alias in Composer either.
- The corpus fixtures must carry the included files for the emulation to
  be exercised at all (today the plugin is a silent no-op on them).

### Non-goals

- The implicit update (above). `merge-scripts` (scripts never run),
  `mergeSuggests` (no output on install), aliases/references extraction
  (resolution only), `prependRepositories` (resolution, and the filter
  lists of `createFilterListPoolFilter` — an include's `composer`
  repository could add a malware list; noted, not emulated).
- A merged root `conflict`/`replace` that targets a locked package:
  Composer's install-mode solve refuses the lock; vivacity has no root
  conflict/replace check at install today (pre-existing gap, HANDOVER);
  the fixture keeps its `conflict`/`replace` off the locked packages.
- Windows: PHP's own `glob()` implementation there is not exercised
  (no Windows job runs the new harness).
- Composer 1 branches of the plugin (`isComposer1`).
- `vcs`/`path` repositories declared in included files (resolution).

## 3. Meta-analysis

Fresh subagent, 2026-09-17, with experiments on open-web-analytics
(real module files, Composer 2.10.3): fourteen findings, folded into
§1–§2:

1. **Textual conjunction is wrong** (major): `"^2.11 || ^1.0, ^2.8"`
   parses as `^2.11 || (^1.0, ^2.8)` and accepts monolog 2.11.0 where
   Composer's `MultiConstraint` refuses it (exit 4 measured) — the same
   for `platform_check.php`'s php lower bound. Structured links.
2. Hence the link merge lives in `vivacity-resolver` (`Intervals`,
   `Constraint`); core keeps glob, autoload/extra/links-as-JSON merging.
3. **Wrong lock check and wrong fallback story** (major):
   `install_policy_problems` is the malware filter; the real check is
   `missing_requirement_info` (already manifest-parametrised). Warm
   vendor + missing merged requirement = Composer exit 4 with lines, no
   update — fidelity, not fallback; the fallback is for the bare vendor
   only. The merge must be computed before the headline.
4. **`--no-plugins` then plugins is a wrong reference with a layout
   plugin** (major): verified with composer/installers (residue left in
   `vendor/`). Pre-seed the plugin alone for the fixture; two-step
   acceptable for the corpus (no layout plugin there, asserted).
5. A Packagist snapshot made with `--no-plugins` lacks the include-only
   packages (major) — no snapshot needed once the reference installs
   from the lock with the plugin pre-seeded.
6. **"Five entries" was wrong** (major): one real case
   (open-web-analytics); invoiceninja's `Modules/` does not exist at the
   pin, leantime has no plugin in its lock, salesagility blocks it,
   concretecms has another plugin. The fixture carries the proof.
7. Gating `update`/`require`/`remove` on the lock misses a project
   without a lock (major): gate on the manifest.
8. Merged root `conflict`/`replace` against a locked package: Composer
   refuses the lock, vivacity has no such check — pre-existing gap,
   documented; the fixture keeps them off the lock.
9. `extra.branch-alias` merged must not reach `RootPackage::detect`.
10. `self.version`: every link section, pretty = root pretty version,
    the `packages[source]` branch keyed by the include's name.
11. Glob details: bytewise (C locale), `.` only explicit, `glob_one`
    needs an `only_dirs` flag, dedup by spelling, Windows uncovered.
12. `array_merge_recursive` exists in vivacity-autoload with a PHP
    divergence — one implementation in core, reused.
13. `harness/corpus.sh:13-15` wrongly says `--no-scripts` silences
    plugin listeners — fixed; the missing-requirement message is
    `Required package … is not present in the lock file`, not
    "compatible set" (that one is for conflict/replace).
14. `prependRepositories` also feeds the install-time filter lists —
    noted as non-goal.

Verified correct by the reviewer: INIT timing and the content-hash from
the file; PRE_INSTALL_CMD merges the dev sections before `doInstall`
(two passes ≡ one pass with `with_dev`); stability flags and root
aliases irrelevant at install; `AutoloadGenerator` reads the merged
root; `installed.php` includes the root's replace/provide (state.rs:324
does too); plugins loaded from installed.json regardless of `--no-dev`;
`allow-plugins: false` → plain library; `corpus-add.sh git <url> <sha>`
keeps the upstream lock; the generator accepts PSR-4 lists.
