# v0.10 — the corpus: how much of the real world stays native

Decided on 2026-09-16 ("go"), after 0.9.0. Opening cadrage: the question
"when can vivacity be used daily by real PHP projects with Composer as
fallback?" has no answer today because nothing measures the proportion of
real locks that install natively — six fixtures and synthetic corpora prove
*parity where it applies*, not *how often it applies*.

## 1. Scope

### Problem

`vivacity install` is safe by construction (identical output, or Composer
run before any write) but its useful coverage is unknown. A project owner
cannot tell whether vivacity will do the work or hand it to Composer, and
we cannot rank what to port next by real-world frequency rather than by
intuition.

### Constraints

- The measurement is `install` from a real `composer.lock`. The baseline
  is named honestly: **Composer 2.10.3 with `--no-scripts`**, plugins
  loaded and **fully active**: `--no-scripts` only sets
  `EventDispatcher::setRunScripts(false)`, which skips the composer.json
  scripts — every plugin listener still runs (verified on the corpus:
  `dealerdirect/phpcodesniffer-composer-installer` and Flex fire on
  `post-install-cmd`, `pestphp/pest-plugin` on `post-autoload-dump`). So
  "native" means "identical to Composer with its plugins working", which
  is what a project gets; a plugin vivacity treats as benign must write
  nothing under that baseline, and the corpus is what proves it. The
  scripts policy (composer.json scripts) is the next cadrage; the corpus
  counts what it will have to cover.
- Both modes a CI uses: with dev packages and `--no-dev` (same dists, no
  extra network).
- Three buckets per project and mode: **native** (0 diff), **fallback**
  (vivacity stopped before any write, with the scope reason), **diff**
  (vivacity wrote something different, or failed where Composer
  succeeded). A `diff` is a release blocker until fixed or reclassified as
  a documented tolerance. Known unread configuration keys (`vendor-dir`,
  `bin-dir`, `preferred-install: source`, `autoloader-suffix` is read)
  become scope issues **before** the first run so they land in `fallback`
  with a reason, never in `diff`.
- Inputs are committed and pinned: `fixtures/corpus/<name>/` holds the
  project's `composer.json`, its `composer.lock` and a `PROVENANCE` line
  (repository, commit or tag, date; for a `create-project` template
  without a lock, the date the lock was resolved once with Composer). The
  root tree (the root autoload rules need their files) comes from a
  codeload tarball at the pinned commit, cached. Nothing is resolved at
  run time.
- The fallback bucket is decided offline (`scope::analyze` reads only the
  lock and the manifest): a static scan classifies all entries in seconds;
  only the projects predicted native are installed twice.
- `--ignore-platform-req=ext-*` on both sides (a missing local extension
  never decides a bucket; the `php` requirement is kept so
  `platform_check.php` is exercised); one pass without the flag counts
  the real platform failures.
- Runs locally on demand (Mac Studio, persistent cache) and before every
  tag (`--check` against the committed report); a `workflow_dispatch` on
  a ~15-entry subset with `COMPOSER_AUTH` from a PAT and Composer/PHP
  pinned as in `ci.yml`. No weekly run, no automatic issue: with pinned
  inputs only the network changes between two weeks.
- `COMPOSER_CACHE_DIR` set explicitly and shared by both tools
  (`fetch::composer_cache_dir` follows `Factory::getCacheDir`); `ref/` and
  `viv/` deleted after each comparison.
- No credentials: auth-gated templates (Magento, Ibexa, Oro, …) are
  listed as excluded with the reason; an entry whose baseline install
  fails deterministically (old lock refused by `allow-plugins`, PHP too
  old) is excluded with the stderr motive, not counted as transient.

### Non-goals

- Resolver parity on the corpus (`update` needs a Packagist snapshot per
  project: the existing fixture machinery).
- Running scripts, or emulating plugin hooks (next cadrage).
- Performance numbers (bench/ owns them; wall time is a side column).
- Windows.
- Representativeness claims beyond the corpus: the report counts projects
  **and** distinct `name@version` packages and distinct plugins, and
  groups projects sharing most of their lock (the Laravel cluster), so
  "% of projects" is never read as "% of the ecosystem".

### Success criteria (observable)

- `harness/corpus.sh [--scan|--only <name>|--check]` runs the corpus
  (`fixtures/corpus/`, ~100 entries) on Linux and macOS and writes
  `docs/corpus/<date>.md`: per mode, the three buckets with counts (by
  project and by distinct package), every fallback reason ranked by
  frequency with the "inert under `--no-scripts`" annotation for plugins,
  every diff with its first lines, the excluded entries with why, the
  projects declaring `scripts` (which events), the platform failures of
  the pass without the flag, per-project wall time of both tools.
- The first report has an empty `diff` bucket in both modes — or every
  entry of it is an issue in this repo with a reproduction.
- The fallback reasons are ranked: the top three name the next ports
  (README "what is next" points at the report).
- `harness/corpus.sh --check` fails when a project leaves the native
  bucket or a diff appears relative to the committed report.
- The cadrage of the scripts policy starts from the report's numbers.

## 2. Plan

1. **`ScopeIssue::Config(key)`** in `vivacity-core::scope`: `vendor-dir`
   (other than `vendor`), `bin-dir` (other than `vendor/bin`),
   `preferred-install` = `source` (or a map with a `source` value),
   `platform` handled already; unit test; HANDOVER row. Fallback, not diff.
2. **`harness/lib/compare.sh`** — `compare_vendor <ref> <viv> <scope>`
   extracted from `diff-vendor.sh` (the three tolerances,
   `--no-dereference`, `include_paths.php` sorted); file modes compared
   explicitly (`stat` inventory like `path-repos.sh`) — decided here, not
   left to `diff -r`; `diff-vendor.sh` calls it, its 6 fixtures still 0
   diff.
3. **`fixtures/corpus/`** — `<name>/composer.json`, `composer.lock`,
   `PROVENANCE`; `tools/corpus-add.sh <kind> <source> <ref>` fetches
   json+lock at a commit (raw.githubusercontent) or, for a template
   without a lock, `create-project --no-install` then `update --no-install`
   once, and writes PROVENANCE. ~100 entries: templates (laravel/laravel,
   symfony/skeleton, symfony/website-skeleton, drupal/recommended-project,
   roots/bedrock, craftcms/craft, statamic/statamic,
   typo3/cms-base-distribution, shopware/production, slim/slim-skeleton,
   laminas/laminas-mvc-skeleton, cakephp/app, yiisoft/yii2-app-basic,
   codeigniter4/appstarter, spiral/app, api-platform/api-platform,
   sulu/skeleton, pimcore/skeleton, mautic/recommended-project,
   contao/managed-edition, neos/neos-base-distribution, bolt/project,
   winter/winter, octobercms/october, …) and applications/tools with a
   committed lock (composer/composer, phpstan/phpstan-src,
   phpunit/phpunit, phpmyadmin, monica, koel, pixelfed, firefly-iii,
   invoiceninja, akaunting, bookstack, kimai, humhub, FreshRSS, nextcloud
   apps, …), pinned by commit; `excluded.txt` for the auth-gated and the
   deterministic failures. `fixtures/corpus/README.md` says what each file
   is and how to add one.
4. **`harness/corpus.sh`** — `--scan`: for every entry, the predicted
   bucket from the lock + manifest (a `vivacity scope` dry path:
   `install --no-fallback` stops before any I/O, its stderr is the
   reason), the `scripts` events, the config keys, the platform
   requirements; the full run: for the predicted-native entries, stage
   the root tree (codeload tarball at the pinned commit, cached under
   `$WORK/corpus/src`), `git init` identical on both sides, `composer
   install --no-scripts --no-interaction --ignore-platform-req=ext-*`
   (plugins on) vs `vivacity install --no-fallback
   --ignore-platform-req=ext-*`, in both modes, `compare_vendor`, wall
   times, one JSON line per (project, mode) in `$WORK/corpus/results.jsonl`,
   `ref/`/`viv/` deleted after each; `--only`; `--check` diffs the
   buckets against the latest committed report.
5. **`tools/corpus-report.py`** — `results.jsonl` → `docs/corpus/<date>.md`
   with stable ordering; the distinct-package and cluster counts; the
   plugin annotation from a static list of script-event-only plugins
   (checked against each plugin's `composer-plugin` class when in doubt:
   `getSubscribedEvents`).
6. First full run, both modes; each `diff` reproduced as a fixture case or
   unit test before its fix; the pass without `--ignore-platform-req`
   for the platform-failure column.
7. **`.github/workflows/corpus.yml`** — `workflow_dispatch` only, the
   ~15-entry subset, Composer 2.10.3 and PHP pinned, `COMPOSER_AUTH`
   from a secret when present, the report as an artifact.
8. Docs: README (the number, its baseline, where it comes from, "what is
   next" from the ranking), HANDOVER (adding an entry, what the corpus
   does not prove, the refresh policy: re-pin yearly, report dated),
   DECISIONS (the corpus as the yardstick; baseline `--no-scripts`
   named; offline scan; local runs), CHANGELOG, CONTRIBUTING.

### Order

1 → 2 (fixtures still green) → 3 (ten entries, then the list) → 4 `--scan`
→ 4 full → 5 → 6 → 7 → 8. Meta-analysis done (§3); review of 4 and 5
before merge. Version 0.10.0 when the first report is committed; tag on
the user's word.

## 3. Meta-analysis

Run on 2026-09-16 by a fresh subagent (cadrage + plan, repository and
web read-only). Eleven findings; the plan above is the amended one.

| # | Finding | Severity | Resolution |
|---|---------|----------|------------|
| 1 | Templates have no `composer.lock` (laravel/laravel, symfony/skeleton, cakephp/app, slim, codeigniter, bedrock, craft, statamic, flarum… all 404): `create-project --no-install` leaves nothing to install from, `composer install` would resolve live, vivacity stops — half the corpus `unavailable`; "nothing is resolved by us" untenable as written | blocking | inputs committed in `fixtures/corpus/<name>/` (json, lock, PROVENANCE); templates resolved **once** by Composer at a dated moment; root tree from a codeload tarball at the pinned commit |
| 2 | `--no-scripts` also silences plugin listeners of script events (`Installer.php`, `AutoloadGenerator.php`, `InstallationManager.php` under `runScripts`): composer-patches, scaffold, bin-plugin, Flex are inert in the baseline; "X % native" is "X % identical to a scripts-less Composer" and the fallback ranking would point at plugins that are not portable without the scripts policy | major | **refuted by the run**: `--no-scripts` only disables composer.json scripts (`Factory`: `$dispatcher->setRunScripts(false)`; `Installer::$runScripts` stays true), plugin listeners fire — dealerdirect, Flex, pest-plugin observed. The baseline is named accordingly; the report annotates plugins with their events, all active; the benign list must be proven under that baseline |
| 3 | The fallback bucket is static (`scope::analyze` reads lock + manifest, `--no-fallback` exits before any I/O): two network installs per project for nothing | major | `--scan` classifies offline; only predicted-native entries are installed |
| 4 | Network and CI limits: GitHub zipball rate limit (1 000/h with `GITHUB_TOKEN`), Actions cache 10 GB / 7-day eviction, runner disk, 6 h/job; shared cache only with an explicit `COMPOSER_CACHE_DIR` | major | local runs on demand + `--check` before a tag; `workflow_dispatch` on a ~15-entry subset with a PAT; explicit shared cache; `ref/`/`viv/` deleted per project |
| 5 | Known unread keys (`vendor-dir`, `bin-dir`, `preferred-install: source`) are not scope issues: they would land in `diff` as "release blockers" though they are documented limits | major | step 1: `ScopeIssue::Config` before the first run |
| 6 | "% of projects" counts Laravel clusters (monica, koel, pixelfed, firefly, invoiceninja, akaunting, bookstack share ~80 % of their packages); a single mode though CI runs `--no-dev` too, and dev plugins decide buckets | major | distinct `name@version` and distinct plugins reported, lock-similarity clusters, both modes |
| 7 | `--ignore-platform-reqs` on both sides suppresses `platform_check.php` and hides the known platform-failure divergence (Composer code 2 vs vivacity 4) | minor | `--ignore-platform-req=ext-*` (keeps `php`); one pass without the flag for the platform column |
| 8 | `unavailable` mixes transient (network) and deterministic (old lock refused by `allow-plugins`, PHP version) | minor | deterministic failures excluded with the stderr motive |
| 9 | Composer/PHP not pinned in the workflow; file modes undefined in `compare.sh` (`unzip` vs `ZipArchive` differ) | minor | pinned like `ci.yml`; modes compared explicitly by a `stat` inventory |
| 10 | Weekly workflow + automatic issue measure rot, not vivacity | minor | dropped; `--check` before each tag |
| 11 | No target value, no refresh policy, a 2026 corpus measures 2026 locks | minor | report dated, yearly re-pin in HANDOVER; the target proportion is the user's decision, written when set |

The reviewer's alternative (committed pairs + offline scan + double
install only where predicted native + local runs) is adopted wholesale;
the plan's own additions are the two modes, the distinct-package unit and
the scripts count.

## 4. Execution log

- 2026-09-16 — Steps 1–2: `ScopeIssue::Config`; `harness/lib/compare.sh`
  with the mode/link inventory, which immediately showed two divergences
  `diff -r` had hidden on the six fixtures (package binaries not chmod'ed
  like `installBinaries`; a zip-extracted link at 0755 where `unzip`
  leaves 0777 on macOS) — fixed.
- Step 3: 106 entries through `tools/corpus-add.sh` (templates resolved
  once with plugins loaded — a Symfony skeleton without Flex's scripts is
  one package, kept as data; `--ignore-platform-req=php` retried and
  noted for templates PHP 8.5 refuses), `excluded.txt` for the rest
  (auth, no lock, unsolvable). One later exclusion: Backpack demo (PRO
  dists behind authentication).
- Step 4: `install --check-scope` (exit 0/3 before any I/O) is the offline
  scan; the scan also records this machine's platform failures so the run
  ignores `php` only where it must. First scan: 52/106 native (dev),
  57/106 (no-dev), and a bug before any install: `install`'s platform
  check knew neither `lib-*` nor `composer-runtime-api` (14 entries).
- The full run (both modes, ~1 h, cached dists) found: `version_normalized`
  leading zeros and `dev-master` (semver 3 keeps both), `%prettyVersion%`
  dist urls, the embedded `symfony/runtime` stub (now the package's own
  template + `extra.runtime`), Flex's `symfony-pack` = metapackage,
  `apcu-autoloader`. All fixed, each with a unit or PHP oracle; the 23
  dev-mode diff entries re-run: 8 native, 15 left — every one of them a
  plugin from `BENIGN_PLUGINS` writing a file under the plugins-on
  baseline (pest-plugin ×6, phpstan/extension-installer ×5,
  dealerdirect ×4). Also refuted here: the meta's claim that
  `--no-scripts` silences plugin listeners (it does not).
- Final numbers (`docs/corpus/2026-09-16.md`): dev 36 native / 15 diff /
  54 fallback; no-dev 56 native / 0 diff / 49 fallback, of 105. Top
  fallback reasons: `vendor-dir` (10), packages without a zip dist (8),
  `bin-dir` (6), `wikimedia/composer-merge-plugin` (4), then Drupal
  scaffold, `symfony/thanks`, `yiisoft/yii2-composer` (3 each).
- Deviations from the plan: no `--check` yet (the report is committed;
  a re-run is compared by hand until the next release), no lock-similarity
  clusters (distinct-package counts only), `diff-vendor.sh` now gives
  vivacity the same plugin flag as Composer (found by the Flex pack rule).
- Open decision for the user: the three writer plugins — emulate (small
  deterministic generators, but `GeneratedConfig.php` embeds absolute
  paths) or drop from `BENIGN_PLUGINS` (those projects go to the
  fallback); either way the fixture baseline should become plugins-on.
