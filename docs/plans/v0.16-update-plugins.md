# v0.16 — `update` / `require` / `remove` honour the plugins (release 0.14.0)

Started 2026-09-18. Level 2 (the resolution commands write the lock; a
silent divergence is the one thing that breaks the promise): fresh
meta-analysis, independent review. Gate for 1.0 (DECISIONS, 2026-09-18).

## 1. Scope

### Problem

`install` consults the plugins (emulated, benign, or fallback before any
write). `update`, `require` and `remove` do not: Composer loads the
installed plugins before resolving, and some of them change what gets
resolved or written — vivacity can write a lock Composer would not, in
silence. Measured on the symfony fixture (Flex 2.x active, warm vendor):
`composer update --no-install` prints `Restricting packages listed in
"symfony/symfony" to "8.1.*"` — Flex's `PRE_POOL_CREATE` filter; a
vivacity update sees the whole pool. The `update.sh` harness never caught
it because `tools/snapshot-packagist.sh` resolves the reference with
`--no-plugins`.

### Reference points (Composer 2.10.3)

- `PluginManager::loadInstalledPlugins` from `installed.json` at
  `Factory::create`; `PRE_POOL_CREATE` dispatched in `PoolBuilder::buildPool`
  with the loaded packages, the request (`getFixedOrLockedPackages`), the
  root; the event's `setPackages` replaces the pool's package list.
- Flex `PackageFilter`: `symfony/symfony` special-cased; a package is
  kept when locked at that version, or absent from `splits`, or when the
  root constraint on it does not intersect `symfony.require`, or
  `symfony/psr-http-message-bridge < 6.4`; otherwise kept only if one of
  its versions (branch alias included) matches `symfony.require`;
  `splits` pruned to the versions whose `<major.minor>.N.0` matches (60
  patch levels tried; `.x` → `next`). `versions.json` from the endpoint
  (`flex.symfony.com` by default; `extra.symfony.endpoint`), cached under
  `cache-repo-dir/flex`.
- Flex `configureInstaller`: `SuggestedPackagesReporter(NullIO)` — no
  suggestion lines on a Flex project's update/require.

### Decision

1. A **fallback for the resolution commands**, symmetric to `install`'s:
   when an allowed plugin present in `installed.json` / the lock / the
   manifest is neither benign for resolution nor emulated for this run,
   vivacity delegates the whole command to Composer (`composer update …`
   with the same arguments, before any write) and says why;
   `--no-fallback` fails instead (exit 3). Unknown plugin → fallback.
2. **Flex's pool filter emulated** (`vivacity-resolver::flex_filter`):
   `versions.json` fetched through vivacity's HTTP with Composer's cache
   layout (`cache-repo-dir/flex/…`, same key as Flex's `Downloader`) so
   that a snapshot can carry it; applied at pool build. The Flex-specific
   guards: native only when, after resolution, the transaction installs
   no package absent from `symfony.lock` (recipes would be applied) and
   `.env.dist` copy does not apply; else fallback before writing. The
   suggestion lines silenced like `configureInstaller` does.
3. **merge-plugin at resolution**: the structured merged links feed the
   root requires (and the stability flags derived from them); an include
   with `repositories` → fallback (prepended repositories not emulated).
4. `require` on a Flex project → fallback (aliases + recipes); `remove` →
   native when the guards of 2 hold.

### Constraints

- The lock written natively stays byte-identical to Composer with the
  plugins active — proven by `update.sh` whose reference is now resolved
  **with plugins** (`tools/snapshot-packagist.sh` gains `--with-plugins`:
  the plugin pre-seeded like `merge-plugin.sh` does, `versions.json`
  captured into the snapshot and served from `file://`).
- Nothing changes for a project without plugins (`update.sh`, `steps.sh`
  unchanged).

### Non-goals

Recipes, `symfony.lock`, Flex aliases on `require`, `.env` handling,
`drupal/core-recipe-unpack`, prepended repositories — all fallback.

### Success criteria

1. `harness/update.sh`: the symfony fixture's reference resolved with
   Flex active (`Restricting packages…` on the reference side), vivacity
   native, lock identical; a variant with `extra.symfony.require` moved
   to a narrower range (both sides re-resolve), lock identical; sylius
   (Flex too) likewise.
2. `harness/steps.sh` cases: `update` on a project with an unknown
   plugin → fallback line and Composer's lock; `--no-fallback` → exit 3,
   lock untouched; `require` on the symfony fixture → fallback; `update`
   on the merge-plugin fixture → native, lock identical to Composer
   (plugin pre-seeded).
3. Corpus: a `--scan-update` mode is out of scope; the report gains a
   column from the manifests: "resolution plugins" per entry.
4. Docs: README (the resolution commands' plugin policy, in the same
   paragraph as install's), CHANGELOG, HANDOVER, DECISIONS (1.0 gate),
   CONTRIBUTING (the "merge-plugin for the resolution commands" item
   closes, Flex recipes item opens), this plan.

## 2. Plan

1. `crates/vivacity-core/src/scope.rs`: `RESOLUTION_BENIGN` list +
   `resolution_issues(project, lock, manifest, plugins_enabled) ->
   Vec<ScopeIssue>` (plugins from installed.json ∪ lock ∪ manifest,
   allowed, not benign, not emulated → issue).
2. `crates/vivacity-resolver/src/flex_filter.rs`: `versions.json` model
   (`splits`, `next`), `prune_splits(symfony_require)`,
   `remove_legacy_packages(packages, root_constraints, locked, ...)` —
   port line by line; unit tests on a captured `versions.json`.
3. Pool build hook: `session.rs` applies the filter when Flex is active
   (`extra.symfony.require` non-empty, `extra.symfony.endpoint` default
   or `flex://defaults`), fetch via the session's HTTP + cache dir.
4. `lib.rs`: `resolve_and_lock` → scope check first (fallback path:
   `composer <argv>` re-exec with the original arguments, `--no-fallback`
   flag on update/require/remove), Flex guards after resolution, merged
   root requires from `merge_plugin::Merged`, suggestions silenced.
5. `tools/snapshot-packagist.sh --with-plugins`, `harness/update.sh`
   reference with plugins, `steps.sh` cases, docs.

### Order

1 → 4 (fallback) → steps cases (prove the guard) → 2 (TDD on a captured
versions.json) → 3 → snapshot with plugins → update.sh symfony/sylius →
merge-plugin at resolution → docs → CI → review.

## 3. Meta-analysis

Fresh subagent, 2026-09-18, with experiments (Flex seeded on the symfony
and sylius fixtures, the three Flex versions of the corpus diffed, the
local Composer cache read). Thirteen findings; the plan is **revised**
accordingly (§5):

1. **Flex 2.x has no `versions.json`** (major): the filter data is the
   `versions` key of each endpoint's `index.json` (defaults:
   `raw.githubusercontent.com/symfony/recipes/flex/main/index.json` and
   `recipes-contrib`), first endpoint wins per key, cached under
   `cache-repo-dir/flex/<key>` as `{body, headers}`; identical in
   1.21.5, 2.9.0, 2.10.0, 2.11.0 (`PackageFilter.php` byte-identical
   2.9 → 2.11). The endpoint list follows `Downloader::__construct`
   (`extra.symfony.endpoint` string/array, `flex://defaults`,
   `SYMFONY_ENDPOINT` env, a non-`.json` string = legacy → fallback).
2. **Activation must not require the default endpoint** (major):
   sylius, thelia, uvdesk, shopware use a custom endpoint +
   `flex://defaults`. Measured on sylius: with Flex the update gives
   0 installs / 43 updates, without it 1 / 49 — **eight packages differ**
   (`symfony/error-handler` v7.4.17 vs v8.1.5, …): today's `update.sh`
   sylius and symfony cases prove parity against an unrepresentative
   reference.
3. Missing from the port spec (major): `SYMFONY_REQUIRE` env with the
   `.x` → `.x-dev` rewrite; `COMPOSER_PREFER_DEV_OVER_PRERELEASE=1`
   forced by Flex on Composer ≥ 2.9 (vivacity reads the env in
   `policy.rs`; must be forced when Flex is active); `ignorePreleases`
   dead on 2.10.3; the `symfony/psr-http-message-bridge` test is a PHP
   **string** comparison `"6.4" > <normalized version>`; `getVersions`
   drops a `splits` entry when no version or all versions survive.
4. **The plugin set at resolution is `installed.json` (+ the global
   one), not the lock or the manifest** (major): `loadInstalledPlugins`
   reads the local repository only; a plugin installed during the run is
   activated on the spot and Flex then re-runs the update
   (`reinstall`). Hence: bare vendor + `update --no-install` →
   unfiltered lock in Composer too; bare vendor + `update` with install →
   filtered — vivacity: fallback when a resolution-affecting plugin is in
   the new lock but not installed. A lock-based inventory would have
   changed `steps.sh`'s behaviour on every symfony/sylius/rector case.
5. **The recipes guard is under-specified** (major): Flex's transaction
   is `symfony.lock` → result set (an install operation for every
   resolved package absent from `symfony.lock`: 123 of 153 on the demo),
   recipes configured from the endpoints' `recipes` index, bundles
   detected by a vendor file scan, uninstalls unconfigure and delete,
   `flex-require*` merged, `unpack()` on every update (a root
   `symfony-pack` with requires edits composer.json **and** the lock),
   `synchronizePackageJson` when `package.json`/`importmap.php` exist,
   `.env.dist` copy. All under `--no-scripts`. Measured: a steady-state
   `update` with install changes only composer.lock. `--no-install`
   never records operations.
6. The install phase of `update` must fall back to `composer update`,
   decided **before** the lock write (`composer install` dispatches
   POST_INSTALL_CMD, not POST_UPDATE_CMD; `--no-audit` is not an install
   option).
7. `require`/`remove` edit composer.json before resolving: a fallback
   must revert the edit first (the command layer decides, not
   `resolve_and_lock`); Flex's `PackageResolver` also rewrites
   `symfony/*` constraints on `require` — fallback.
8. Benignity is per command (`(command, plugin) → Benign | Emulated |
   Fallback`): `drupal/core-recipe-unpack` acts on `require` only;
   `php-http/discovery::postUpdate` edits composer.json on `--no-install`
   over a stale vendor.
9. Harness: Flex ignores `file://` endpoints (only HTTP 200 bodies);
   `php -S` + `SYMFONY_ENDPOINT` + `secure-http: false` in the harness
   home works; the reference needs Flex pre-seeded like
   `merge-plugin.sh`; editing `extra.symfony.endpoint` would change the
   content-hash.
10. The symfony fixture cannot discriminate as-is (root constraints
    `8.1.*` = `symfony.require`, 0-line diff with or without Flex); the
    variant needs wider root constraints (`^8.0` + `symfony.require
    8.0.*`: 926-line diff).
11. Inventory: merge-plugin 4 projects; `extra.symfony.require` without
    Flex installed (prestashop, wallabag, phpdocumentor) → no filter;
    Flex alias-resolves `update`/`remove` arguments (`PackageResolver`,
    throws on an unknown slash-less name) — documented divergence;
    global plugins out of scope.
12. Fallback argv: strip `--no-fallback`, `--offline`, internal flags;
    `--working-dir` → `-d`; `--no-blocking` exists in 2.10.3; exit 3
    reserved for `--no-fallback`.
13. Recommendation: ship the fallback and the filter for `--no-install`
    now; the with-install guard (recipe index + bundle scan + uninstalls
    + sync) as its own item.

Verified correct: `PRE_POOL_CREATE` placement (after loading and
temporary constraints, before advisory/list filters; vivacity's hook
point `pool.rs` before `Pool::new`); it fires on install too but the
locked short-circuit makes it a no-op there; partial update locks the
non-allowlisted packages; `configureInstaller` silences suggestions only
(PRE_UPDATE_CMD, not under `--dry-run`); `--no-scripts` keeps plugin
listeners; recipe-unpack `require` only; the benign list for resolution;
merge-plugin `prependRepositories` → fallback; `allow-plugins`
semantics reusable.

## 5. Revised scope (after the meta-analysis)

Release 0.14.0:
- **A. Resolution fallback** (decision 1) with the plugin set from
  `installed.json` (+ `$COMPOSER_HOME/vendor/composer/installed.json`),
  `(command, plugin)` table, decided in the command layer before any
  write or after reverting `require`/`remove`'s edit; with install, a
  resolution-affecting plugin present in the new lock but not installed
  → fallback; the install-side scope analysis of the resolved lock runs
  **before** the lock write and falls back to `composer update` on any
  issue.
- **B. Flex filter for `update --no-install`** (and `remove
  --no-install`): endpoints resolved like `Downloader`, `index.json`
  `versions` fetched and cached in Composer's layout, `SYMFONY_REQUIRE`,
  the string comparison, the pruning rules, `COMPOSER_PREFER_DEV_OVER_PRERELEASE`
  forced, suggestions silenced; guards: no `flex-require*`, no root
  `symfony-pack` with requires, no `.env.dist` case, else fallback.
  Flex `update`/`remove` **with install** and every `require` → fallback
  until the with-install guard exists (own plan).
- **C. merge-plugin at resolution**: merged root links + stability
  flags (`StabilityFlags::extractAll` port), fallback on an include
  with `repositories`.
- **Harness**: `update.sh` reference with Flex pre-seeded and the index
  served by `php -S` (`SYMFONY_ENDPOINT`, `secure-http: false`), the
  symfony variant with widened root constraints, sylius; `steps.sh`
  cases for the fallback paths and `--no-fallback`.

Later (own plan): Flex with install (recipes index, bundle scan,
uninstalls, `synchronizePackageJson`, `.env.dist`), Flex aliases on
`require`, `drupal/core-recipe-unpack`.
