# Les lignes `  - Downloading` — cadrage

## 1. Le fait, mesuré le 2026-09-30

Composer imprime, avant le bloc des opérations, une ligne par paquet dont
l'archive n'est **pas** dans son cache de fichiers :

    FileDownloader.php:193
    if ($this->cache !== null && ($checksum === null || $checksum === '' ||
        $checksum === $this->cache->sha1($cacheKey)) && $this->cache->copyTo(...)) {
        // touché : "  - Loading X (v) from cache", en VERY_VERBOSE seulement
    } else {
        $this->io->writeError("  - Downloading <info>X</info> (<comment>v</comment>)");
    }

Mesuré sur la fixture laravel (109 paquets, deux runs à cache vide) :
- **109 lignes**, en **deux blocs** : tous les `- Downloading`, puis tous les
  `- Installing` ;
- **ordre identique entre deux runs à froid**, et **identique à celui des
  lignes `- Installing`** — donc l'ordre de la transaction, que vivacity
  reproduit déjà ;
- à cache **chaud** : zéro `- Downloading`, et 109 `- Loading … from cache`
  visibles seulement en `-vv`.

vivacity n'imprime jamais ces lignes. Trois harnais les filtrent de la sortie
de Composer (`flex-install.sh`, `bin-plugin.sh`, `flex-update.sh`), ce qui rend
l'écart invisible au banc.

**Correction d'une note de banc** : le commentaire « cache froid » de ces
filtres est juste ; mais ma première mesure « à chaud » ne l'était pas (variable
de shell non définie entre deux appels), et m'a fait croire un instant que
Composer imprimait ces lignes même à chaud. La source et la mesure refaite
disent non.

## 2. Pourquoi c'est fermable sans coût

`Fetcher::dist_bytes_of` (`crates/vivacity-core/src/fetch.rs:293`) prend déjà
exactement la décision de Composer : lecture du fichier de cache, sha1 comparé
à celui du lock, entrée corrompue jetée, `Provenance::Cache` sinon réseau.
L'information existe donc ; elle n'est pas imprimée.

Et comme Composer produit un **bloc contigu** avant le bloc des opérations,
imprimer nos manques après la phase de téléchargement, triés par index de
transaction, donne la **même suite d'octets** — seul le moment d'affichage
diffère, pas la sortie. Aucune E/S en plus : chaque tâche remonte déjà sa
provenance.

## 3. Périmètre proposé
- Collecter `(index de transaction, nom, version jolie)` pour chaque
  `Provenance` autre que `Cache`, puis imprimer le bloc avant les lignes
  d'opérations.
- `getFullPrettyVersion()` : même texte que la partie paquet des lignes
  `- Installing`, que `operation_lines` produit déjà — à réutiliser, pas à
  redériver.
- **Retirer les trois filtres du banc** : c'est la preuve. Un filtre qui
  disparaît est un écart qui se ferme.

## 4. Questions ouvertes à trancher avant d'écrire
1. Le paramètre `$output` de `FileDownloader::download` : dans quelles phases
   vaut-il false ? (Composer télécharge aussi en phase d'install pour certaines
   stratégies.) Une ligne imprimée deux fois ou jamais se joue là.
2. Un paquet `path`, un métapaquet, un paquet sans dist : aucun
   `FileDownloader`, donc aucune ligne — à vérifier.
3. `--no-progress`, `--quiet`, `-v` : la ligne est en verbosité normale, mais
   `$output` peut dépendre du reste.
4. Notre phase de téléchargement échoue-t-elle parfois avant d'avoir la
   provenance de tous les paquets ? Le bloc doit alors ne pas être imprimé à
   moitié.
5. Le `- Loading … from cache` de `-vv` : hors périmètre (vivacity n'a pas
   `-vv`), à écrire comme tel.

## 5. Critère de succès
Les trois filtres retirés, et `diff-vendor.sh` à cache vide des deux côtés
donnant une stderr identique à l'octet sur un projet de ~109 paquets.
